# ADR-002: The in-repo roadmap derives every status from the disk, with no external tool

- **Status:** accepted
- **Date:** 2026-07-20

## Context

The kit tracks one change at a time (`docs/features/<change-id>/` → PR → `archive/`), and the `aidakit:orchestrator` picks "the next ready change" by inspecting those real artifacts. But there was no artifact for **planning above the change**: no way to declare "these changes make up the Checkout feature, which belongs to the Payments epic", no shared view of what is in progress across the project, and no roadmap. The team wants that — but explicitly **without adopting Jira/Confluence**; everything should live in the repo, versioned and reviewed in PRs like the rest.

The central hazard of any status board is drift: the card says "in progress" while the code shipped two weeks ago, because a status is a field someone has to remember to move. The kit already rejects this pattern elsewhere — the doc leash makes "the truth is the disk, not the status the model wrote". A roadmap should inherit that discipline.

## Decision

The roadmap is **versioned markdown in `docs/roadmap/`**: epics (`epics/EPIC-<slug>.md`) declare their features, and each feature lists the **changes that deliver it by `change-id`** — the single key (§2.7) that already ties branch = PR suffix = `docs/features/<id>/` = archive dir. The roadmap **reuses** that key and never mints a parallel ID.

No item carries a hand-written status. `governance/validators/derive-roadmap-status.js` **derives** each change's status from the disk (strongest evidence first): archived → `done`; open PR for the id → `in-review`; `docs/features/<id>/` exists → `in-progress`; a branch but no artifacts → `planned`; declared but nowhere → `backlog`. Features and epics **aggregate** their children. Git is only a heuristic for PR/branch and degrades gracefully to disk-only when absent. `ROADMAP.md` is a **generated** Now/Next/Later snapshot (DOCS.md §5: manual snapshots die — this one is regenerated by `aidakit:roadmap`, never edited). The `aidakit:orchestrator` reads the roadmap to order the ready set by epic priority.

## Consequences

- Positive: the roadmap cannot drift — status is a function of reality, so moving an item means doing the real work (author the change, open the PR, archive it); no external tool, no license, no sync; planning reuses the one key the kit already trusts; the orchestrator gains an explicit priority order instead of inferring one.
- Negative:
  - Status granularity is bounded by what the disk reveals (in-progress vs. in-review depends on a git/PR signal) — **Accepted** (finer states would reintroduce hand-maintained fields, the very drift we reject).
  - A change-id declared in an epic before any artifact exists shows as `backlog`/orphan — **Mitigated** (`--strict` flags orphans as gaps; it is intent, legitimately not-yet-started).
  - The `gh`/git heuristics are best-effort and environment-dependent — **Accepted** (with no git, the roadmap still derives done/in-progress from `archive/` vs `features/`, never errors).

### Review trigger

Teams asking for a status the disk cannot express (e.g. "in QA", "blocked on design") often enough that a small declared-status escape hatch would pay for its drift risk; or the orphan rate staying high because epics are declared far ahead of any change.

## Alternatives considered

| Option | Pros | Cons | Cost to undo |
|---|---|---|---|
| External tool (Jira/Confluence) | Rich boards, integrations | The explicit non-goal; drift between tool and repo; license, context-switch, no versioning with the code | high |
| Hand-written `status:` field per item | Simple; any state expressible | The Jira drift problem in-repo: the field lies the moment someone forgets to update it | medium |
| A single flat backlog file (no epic/feature hierarchy) | Minimal | No grouping; can't answer "what's the status of Payments"; doesn't scale past a handful of changes | low |
| Derive status but store it back into the files (cache) | Fast reads | A cache that can go stale reintroduces drift; the derive is already cheap (a disk walk) | medium |
