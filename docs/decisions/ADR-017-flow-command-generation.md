# ADR-017: Flow-command generation — the `flow-` group widens to "flow mechanism family", naming shifts activity-based → flow-name-based

- **Status:** accepted
- **Date:** 2026-07-27

## Context

[ADR-005](ADR-005-command-namespacing.md) locked the `flow-` prefix on two derived rules: (1) **group-membership** — a command belongs to the `flow` group iff it drives the engine (`node governance/cli.js start <flow>`); (2) **naming** — the individual command name is derived from the **activity** (`build`), not the **flow name** in the YAML. That naming was a leftover from before the engine had named flows: `commands/flow-build.md` drove *both* the `fast` and the `full` flow (`start fast …` / `start full …`), so the command surface did not line up 1:1 with the flow YAMLs it wrapped (`governance/flows/fast.yaml`, `full.yaml`, `design.yaml`, `docs-onboarding.yaml`).

Two concrete costs followed from this. First, boilerplate at the point of use: starting the fast flow required typing `flow-build start fast request="…"` (via the old `commands/flow-build.md`) — the `start`, the `fast`, and the `request=` key are all mechanically derivable from the flow YAML's own `flow:` and `inputs:` fields, yet the human supplied them every time. Second, the surface did not scale: ADR-005's own "Extensibility contract" promised that a consumer authoring `.aidakit/flows/<my>.yaml` "follows the same rule in their own plugin namespace" — but no mechanism existed to turn a project flow into a command; a consumer had to hand-author one, duplicating the wrapper prose with no tool keeping it in sync with the flow it wrapped.

`docs/features/per-flow-commands/design.md` introduces a single generator (`governance/commands/render-flow-command.js` + `generate-flow-commands.js`) that renders one `flow-<name>.md` per flow YAML from its own `flow:`/`description:`/`inputs:` fields, plus a `flow-sync` utility that runs the generator in consumer mode. `flow-sync` legitimately wears the `flow-` prefix (it is the generator's front for the flow mechanism), yet it does **not itself drive the engine** — it renders commands that do. This does not fit ADR-005's mechanical grouping criterion as written, and the activity-based naming (`flow-build`) does not fit a generator that renders exactly one command per flow YAML. Both rules need to widen; this is the recorded contract-change escalation the brainstorm gate flagged (`.aidakit/tasks/per-flow-commands/brainstorm.json`, `escalations[0]`).

## Decision

**(a) Group-membership widens** from "the command drives the engine" to "the command belongs to the **flow mechanism family**": the orchestrator shortcuts (`flow-fast`/`flow-full`/`flow-design`, which drive the engine) *and* the flow-command generator's front (`flow-sync`, which does not drive the engine but generates the commands that do) both legitimately wear the `flow-` prefix. The mechanical-grouping *spirit* is unchanged — membership is still derived from a reproducible rule, never a hand-picked list — only the rule's boundary widens to cover the generator's own front door.

**(b) Naming shifts from activity-based to flow-name-based**: exactly one `flow-<yamlFlowName>` command per non-opted-out flow YAML, generated by one template (`renderFlowCommand`) driven only by the flow's own `flow:`/`description:`/`inputs:` fields — never a hardcoded `flowName === "fast"` table. Concretely: `commands/flow-build.md` (which drove both `fast` and `full`) is removed; its coverage splits into `commands/flow-fast.md` (carries `register`, fast's own `mode=register`) and `commands/flow-full.md`; `commands/flow-design.md` survives (its name already equalled the flow name) but becomes generated instead of hand-authored. `docs-onboarding` gets no generated command — an explicit per-flow opt-out marker (`emit_flow_command: false`) keeps `aidakit:docs` the single onboarding door, per ADR-005's own utility classification of `docs`.

Both points **supersede ADR-005** on those two specifics; the flat `flow-` syntax itself (ADR-005's locked spike outcome) and the mechanical-grouping spirit are unaffected and continue to bind.

**Mechanism, briefly** (full spec: `docs/features/per-flow-commands/design.md`): a single generator loads each flow through the engine's own `parseFlowFile` (no second YAML reader), derives `positionalKey` (the first required input) and `hasRegister` (does an input's `values` enum include `"register"`?) from the YAML, and renders one template in two modes — `kit` (governance/flows/*.yaml → committed commands/) and `consumer` (.aidakit/flows/*.yaml → .claude/commands/, the mode `flow-sync` drives). A sentinel (`<!-- aidakit:generated … -->`) marks every generated file; the generator refuses to overwrite a target lacking it (protects hand-authored files) and refuses a consumer flow named `fast`/`full`/`design` (protects the shipped built-ins from shadowing). A byte-drift test (`governance/__tests__/flow-command-generation.test.mjs`) fails if any committed built-in drifts from re-running the generator.

## Consequences

- **Positive:** the command surface lines up 1:1 with the flow YAMLs — one generated `flow-<name>.md` per flow, with no manual sync step; ADR-005's extensibility contract finally has a mechanism (`flow-sync` gives a consumer flow a command with no hand-authoring); the generator + drift test keep the built-ins honest against template or flow-YAML drift; the start verb becomes implicit (`/aidakit:flow-fast <request>` — no `start`/`fast`/`request=` typed), removing exactly the boilerplate cost that motivated this change.
- **Negative (Accepted):** `flow-build` is a **breaking rename** for any consumer bound to that name (psim-kernel) — no bridge alias, mirroring ADR-005's own direct-break, rejected-alias stance. Mitigated by the migration note below: the split names are one plugin-sync away.
- **Negative (Accepted):** `docs-onboarding` is a real, startable engine flow (`cli.js start docs-onboarding …` still works, `flow list` still shows it) with **no** generated shortcut command — a documented asymmetry, the price of keeping `aidakit:docs` the single onboarding door rather than opening a second, engine-driven one.
- **Negative (Mitigated):** a genuine build request whose intent literally begins with the word `register` cannot be started through the `flow-fast` implicit-start shortcut (it is read as the `register` verb, which only `flow-fast` carries). Mitigated: the operator uses explicit phrasing, or the `register` block deliberately; a narrow, documented edge, not a silent trap (`design.md` §3.4).

## Alternatives considered

| Option | Pros | Cons | Cost to undo |
|---|---|---|---|
| Generic orchestrator command + flow arg (`/aidakit:flow start <x>`) | One command instead of N | Owner topology decision already settled against it (brainstorm Q3); each `flow-<x>` stays self-contained by design | medium |
| Bridge alias so the old `flow-build` command keeps resolving | No break for psim-kernel today | Doubles the autocomplete clutter ADR-005 removed; two names for one concept, forever or until a second break | medium |
| Hand-author each per-flow command (no generator) | No new runtime module | No single source of truth — the command drifts from its flow YAML the first time either changes; the exact defect this ADR's mechanism closes | high |
| Emit a `flow-docs-onboarding` command too | Full 1:1 symmetry with every flow YAML | Opens a second, engine-driven onboarding door, contradicting ADR-005's classification of `aidakit:docs` as the single-door utility | low |
| Auto-detect kit vs. consumer mode instead of an explicit `--mode` flag | One fewer flag to pass | Not fail-closed — an auto-detect heuristic could write the committed built-ins from a consumer checkout by accident; explicit is testable | low |
