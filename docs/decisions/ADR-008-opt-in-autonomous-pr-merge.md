# ADR-008: Autonomous PR merge, opt-in per project — scoped supersession of GOVERNANCE.md §1 rule 1

- **Status:** accepted
- **Date:** 2026-07-24

## Context

[GOVERNANCE.md](../../GOVERNANCE.md) §1 rule 1 is categorical: *"Merging a PR. Never the agent's. The agent delivers the PR URL and stops. The human is the final gate."* The mechanics reinforce the doctrine in two places: the tail of both flows ends in a merge `human_gate` ([governance/flows/full.yaml:283-293](../../governance/flows/full.yaml), [fast.yaml:213-224](../../governance/flows/fast.yaml)), and the `pre-bash` hook blocks `gh pr merge` unconditionally ([hooks/pre-bash.js:47-50](../../hooks/pre-bash.js) as of the pre-this-change baseline).

That is correct by default. But some projects trust the kit's pipeline and want the tail to merge on its own, eliminating the manual touch on every change. There was no way for a project to declare that preference — the rule was global and the enforcement absolute.

This change's owner (change `configurable-pr-automation`) **consciously requests a scoped supersession** of that rule: authorize autonomous merge **only** for projects that opt in via configuration. This is escalation 2 of [GOVERNANCE.md](../../GOVERNANCE.md) §1 ("superseding or contradicting a rule: the agent proposes, the human decides") — resolved by the human, who authorizes the supersession. This ADR **names the conflict** with §1 rule 1 and records it; the agent did not decide this alone.

The conflict, explicit: §1 rule 1 says merge is **never** the agent's; this decision lets the agent merge **when, and only when**, the project declares `pr.auto_merge: true` in its `aidakit.config.yaml`. Outside that opt-in, §1 rule 1 continues to hold in full.

## Decision

**1. Per-project opt-in supersedes §1 rule 1, scoped.** A project that declares `pr.auto_merge: true` in `aidakit.config.yaml` authorizes the flows to merge autonomously at the `merge` step. Absent the `pr:` block (or with `auto_merge: false` — the default), §1 rule 1 holds in full and the merge stays at today's `human_gate`. The supersession is **strictly scoped** to the opt-in project: no project is affected without an explicit opt-in, and the kit's own repository (no `aidakit.config.yaml`) stays on the human gate.

**2. Trust source: the opt-in must be a PRIOR, already-merged decision — never something a PR's own diff can grant itself (round-2 fix, security veto).** `pr.auto_merge` is read from the repo's **trusted base branch** (`governance/pr/pr-config.js`'s `resolveBaseRef` + `git show <base-ref>:aidakit.config.yaml`) — **never** from the PR's own working tree or checked-out branch. Concretely: a PR that adds `pr.auto_merge: true` to its own diff is **not** auto-merged by that addition — a human merges that first PR, same as today; only **after** that config is committed on the base branch do later PRs see the opt-in and route through `auto_merge`. Base-ref resolution order: an explicit `AIDAKIT_BASE_REF` override; else the remote's default branch, **kept as the remote-tracking ref** (`origin/HEAD` resolved, e.g. `origin/main` — round-3 correctness fix: an earlier draft stripped the `origin/` prefix and returned the bare local branch name, which is wrong, since a locally-checked-out branch of the same name — e.g. a PR branch happening to be named `main` — could diverge from what origin actually has; keeping the remote-tracking ref means the read always reflects the last-fetched state of the real remote, never a possibly-diverged local branch); else a local `main` (only reached with no usable remote); else a local `master`. Any edge that doesn't resolve cleanly — not a git repository, no remote and no `main`/`master`, an unreadable ref, the file absent on the base, a git error, a detached `HEAD` with none of the above — resolves to `false` (the human gate), never an error and never a guess.

**3. Conditions and guardrails of the autonomous merge.** The autonomous merge only proceeds when **all** of the following hold:
- **Position in the flow guarantees the rigor:** the merge step is only reachable after the review bench + hardening + doc-gate (the tail is `… → check_docs → pr → merge`). The autonomous merge does not re-run or loosen those gates.
- **PR mergeable per the host:** no required check failing, no `CHANGES_REQUESTED` review, no branch-protection block, `MERGEABLE` state. Verified read-only on the host before acting.
- **The host's normal mechanism, never a privileged bypass:** uses `gh pr merge` respecting the host's own rules. It passes **the same [GOVERNANCE.md](../../GOVERNANCE.md) §4 guardrails** a human merge would — **no** `gh pr merge --admin` (bypasses branch protection), **no** `--no-verify`, **no** `AIDAKIT_BYPASS`. (`gh pr merge` has no `--force` flag; earlier drafts of this ADR/design/proposal named it alongside `--admin`/`--no-verify` by mistake — corrected here.)
- **Explicit failure, never silent.** Any doubt or failure (gh not configured, no token/permission, branch protection blocks, PR not mergeable, changes-requested) falls into the `human_gate`, reporting why. There is never a silent merge nor a bypass attempt.

**4. Mechanical enforcement updated in lockstep — and stated HONESTLY (round-3 correction, expanded round 4; the owner has decided this posture, see §Consequences).** For the mechanics not to contradict the doctrine:
- `hooks/pre-bash.js` gains a **config-gated** exception on the `gh pr merge` rule: released only when the repo's **base branch** declares `pr.auto_merge: true` (never the working tree — see point 2). The carve-out is a **FAIL-CLOSED guardrail**: it permits ONLY a recognized-safe literal `gh pr merge <safe-args>` shape (real shell-word tokenization — quotes/escapes collapsed the way a shell would — then an ALLOWLIST of safe shapes, never a raw-string substring scan), and blocks forbidden flags (`--admin`/`--admin=...`/`--no-verify`) AND any ambiguous/unrecognized/obfuscated shell construct. The hardened classes, each closing a live-demonstrated bypass:
  - **Quote-splicing / backslash escaping** (round 2): `gh pr merge --adm''in` / `--adm\in` both collapse to the literal token `--admin` in a real shell before `gh` ever sees it — a raw-string substring scan never caught this; real tokenization does.
  - **Brace grouping and shell reserved words** (round 3): `{ gh pr merge --admin; }`, `if true; then gh pr merge --admin; fi` (a reserved word puts `gh` outside the expected first-token position) — any occurrence marks the whole parse ambiguous.
  - **`eval`/`sh -c`/`bash -c` with the payload INLINE in the visible command text** (round 3, narrowed round 4 — see the honest-limit bullet below for what this does NOT cover): `eval 'gh pr merge --admin'`, `sh -c 'gh pr merge --admin'`, `bash -c 'gh pr merge --admin'` re-parse their own argument as shell, and since the payload is literally present in the outer command text, the trigger fires and the reinterpreting-leader check blocks them.
  - **Obfuscating `gh` itself so the OLD trigger missed the command entirely** (round 3): `X=gh; $X pr merge --admin`, `gh${IFS}pr${IFS}merge --admin`, `$(echo gh) pr merge --admin`, `` `echo gh` pr merge --admin `` — none contain the literal substring "gh pr merge", so a trigger anchored to that adjacency never even dispatched them for analysis. Fixed by broadening the trigger to "raw text contains both `gh` and `merge` as substrings, case-insensitive" (narrow enough that `git merge $branch`/`gh pr view $PR`/`gh pr list | grep merge` never match it) — once dispatched, the existing ambiguity checks catch the obfuscation.
  - **A benign command-wrapper prefix before the invocation** (round 4 — closes a regression the round-3 rewrite introduced): `command gh pr merge --admin`, `env gh pr merge --admin`, `builtin gh pr merge --admin`, `exec gh pr merge --admin`, `nice gh pr merge --admin`, `nohup gh pr merge --admin`, `command -p gh pr merge --admin` all still genuinely invoke `gh pr merge` — they just move it off the first token position. The old raw-substring rule caught these (it matched anywhere in the text); round 3's positional `tokens[0..2]` check missed them. Fixed by scanning for the `gh` binary token anywhere in a simple command's token list, not only at the start — works for any wrapper without enumerating them, while a quoted mention (`echo "run gh pr merge"`) still never matches, since the quoted text collapses to ONE token, never three separate consecutive ones.
  - **Three PLAIN-TEXT (non-obfuscated) standard `gh` invocation forms** (round 5 — security veto, confirmed live against the real installed `gh` binary; these are documented, ordinary `gh` usage, not obfuscation): (a) a **path-qualified `gh` binary** — `/opt/homebrew/bin/gh pr merge --admin`, `./gh pr merge --admin`, `bin/gh pr merge --admin` — still genuinely `gh`, just invoked by path; matching the exact string `'gh'` missed all of these. Fixed by matching the token's **basename** instead. (b) a **standard global flag before the subcommand** — `gh -R owner/repo pr merge --admin`, `gh --repo owner/repo pr merge --admin` — `-R`/`--repo` are valid before the subcommand per `gh`'s own documented usage, which puts a token between `gh` and `pr` and defeats a strict three-consecutive-token match. Fixed by tolerating arbitrary tokens between the found `gh` token and the `pr`/`merge` pair (not replicating `gh`'s full flag grammar, which would be fragile to keep in sync) while keeping `pr`+`merge` themselves strictly adjacent — specific enough that unrelated `gh`/`git` usage doesn't produce that literal two-word sequence by accident (re-confirmed against the same 5 innocent-mention regression cases). (c) **argument injection via `xargs`** — `printf 'pr\nmerge\n--admin\n' | xargs gh` reaches real `gh` with the merge args arriving from stdin, invisible to the tokenizer, even though the command text contains "gh"/"merge" substrings and trips the trigger. `xargs`, as the leader of any simple command in the parsed pipeline, is now treated the same as `eval` — a generic argument-injection primitive that marks the whole analysis ambiguous.
  This forbidden-flag/ambiguity check runs **before**, and independently of, the `AIDAKIT_BYPASS` check — a bypass can never rescue it (round-2 fix, tester finding). **This carve-out is a deliberate, scoped exception to the hook's default fail-open** — [GOVERNANCE.md](../../GOVERNANCE.md) §4 declares "when in doubt, allow" in general, but for `gh pr merge` this ADR inverts that to **fail-closed**. The pointer §4 carries names this explicitly. This is **not** the `AIDAKIT_BYPASS` path (a logged, conscious human override) — it is a permission declared by config and recorded by this ADR.
  - **Honest limit, stated here rather than overclaimed (round-3 quality finding, corrected further round 4 — do not overclaim).** This hardening covers the classes above — it is not, and does not claim to be, an exhaustive shell sandbox. In particular (round-4 correction): **`source ./file`, `. ./file`, `bash ./file`, `sh < file`** — the non-`-c`, file/stdin-sourced forms — are **NOT caught**, and an earlier round-3 draft of this ADR/design.md/the hook's own comments incorrectly implied they were hardened alongside `eval`/`sh -c`/`bash -c`. They are not the same: `source`/`.` take a **filename**, not an inline string to evaluate, so when the actual payload (`gh pr merge --admin`) lives inside the sourced file, the OUTER command text carries no `gh`/`merge` substring at all — the trigger never fires, and this hook has no way to inspect file/stdin contents without blocking all script execution (not this hook's job). This is the SAME NATURE of residual as an agent bypassing `gh` and calling the host's API directly — both are "the payload isn't in the text this hook can see." A `pre-bash` hook cannot robustly stop a malicious or prompt-injected in-process agent from obfuscating shell beyond what this parser understands, hiding the payload in a file/stdin, or skipping `gh` and calling the host's merge API directly — that limitation is a pre-existing property of **every** rule in this hook, not specific to this carve-out. See §Consequences for the recorded, owner-accepted residual and the actual primary controls.
- [GOVERNANCE.md](../../GOVERNANCE.md) §1 rule 1 and §4 (the `gh pr merge` line) gain a pointer to this ADR, so the hierarchy of truth stays self-describing ([DOCS.md §2](../../DOCS.md) rule 5) — doctrine and ADR must never diverge silently.

**5. Realization.** In the engine, a `human_gate` always pauses (it does not skip itself by config), so the decision is realized by a deterministic `runs` gate (`merge_route`, reads the config via `governance/validators/check-pr-automation.js`) followed by an `invoke` `auto_merge` (new skill `aidakit:merge`, opt-in), **preserving the `merge` `human_gate` as the universal fallback**. `aidakit:ship` remains "never merges" — autonomous merge lives only in `aidakit:merge`. Details in [docs/features/configurable-pr-automation/design.md](../features/configurable-pr-automation/design.md).

## Consequences

- Positive: projects that trust the pipeline eliminate the manual touch on the tail via opt-in, without losing any guardrail; the exception is **recorded, not silent**; the default (no config) is untouched, so no existing project is affected; the opt-in cannot be granted by a PR's own diff (point 2) — it is always a prior, already-merged, auditable decision; consumer-authored flows inherit the same config-gated routing pattern.
- Negative:
  - The agent can now merge for opt-in projects — a scoped erosion of "the human is the final gate" — **Accepted** (explicit opt-in, declared in config and recorded by this ADR; the default is unchanged; every §4 guardrail still applies; any doubt falls to the human).
  - The `gh pr merge` block in the hook is no longer absolute — **Mitigated** (config-gated, fail-closed; `--admin`/`--no-verify` stay blocked via tokenized allowlist matching, hardened against the specific obfuscation classes named in point 4, and independent of `AIDAKIT_BYPASS`; malformed config → blocked).
  - The opt-in now depends on `git` being available and the base ref resolving — **Mitigated** (any git/resolution failure → `false`, the human gate; the kit already depends on `git` elsewhere, e.g. `derive-roadmap-status.js`).
  - [GOVERNANCE.md](../../GOVERNANCE.md), WORM-ish doctrine, is edited — **Accepted** (only a scoped pointer is added; the supersession is the entire point of this decision; [DOCS.md §2](../../DOCS.md) rule 5 requires the doctrine not to diverge from the ADR).
  - The autonomous merge depends on the host's mergeability signal being correct — **Mitigated** (any doubt → human gate; no `--admin` to bypass protection).
  - **The hook's hardening has a residual: it is not a sandbox against a hostile actor — ACCEPTED, explicitly, by the owner (round-3 security/quality finding, expanded round 4; do not overclaim this guarantee).** A malicious or prompt-injected in-process agent can, in principle, obfuscate shell beyond what `hooks/pre-bash.js`'s parser understands, bypass `gh` entirely and call the host's merge API directly, or **hide the payload inside a file/stdin this hook never reads** (`source ./evil.sh`, `. ./evil.sh`, `bash ./evil.sh`, `sh < evil.sh` — round-4 correction: an earlier round-3 draft implied these were hardened; they are not, since `source`/`.` take a filename, not inline text, so the outer command carries no "gh"/"merge" substring for the trigger to catch) — no `pre-bash` hook is a sandbox, and this limitation is shared by **every** rule in this hook (force-push, `--no-verify`, `rm -rf`, ...), not specific to the merge carve-out. The owner's decision: harden the demonstrated/common obfuscation classes that carry their payload in the VISIBLE command text (rounds 2–4 above), state the guarantee accurately rather than claim exhaustiveness, and accept the file/stdin-indirection and API-bypass residual rather than chase an unreachable "provably complete" parser (which would require blocking all script execution to achieve). The **primary** controls against a hostile actor are (a) the `aidakit:merge` skill's own discipline — it only ever invokes a plain `gh pr merge` (optionally a safe merge-method flag), never a forbidden flag, by construction of what the skill is instructed to do — and (b) the base-branch opt-in itself (point 2: a hostile actor would need to land the opt-in on the trusted base first, through the same review gates as any other change). The hook is **defense-in-depth** on top of those two, not the security boundary.
  - **Round-4 regression fixed before it shipped: a benign command-wrapper prefix (`command`/`env`/`exec`/...) defeated the round-3 positional check** — **Mitigated** (found by the round-3→round-4 review cycle itself, before merge; fixed by scanning for the `gh`/`pr`/`merge` triple anywhere in a simple command's tokens, not only at the start; regression-tested for all 7 wrapper forms plus 5 innocent-mention forms that must NOT be falsely blocked).

### Review trigger

If a host changes the semantics of its mergeability signal, or if the kit ever wants **org-wide** automation (not per-project) instead of opt-in via `aidakit.config.yaml`, revisit in a new ADR — don't widen the scope here. Same if demand emerges for the autonomous merge to skip one of the positional gates (bench/hardening/doc-gate): that would be a new decision, not an extension of this one.

## Alternatives considered

| Option | Pros | Cons | Cost to undo |
|---|---|---|---|
| Keep merge human-only (status quo) | Zero risk; §1 rule 1 intact | Doesn't serve projects that trust the pipeline — the owner's concrete request | n/a |
| Global kit-wide toggle (env/flag) | One place | Affects the kit's own repo and every consumer at once; contradicts the per-project model of `aidakit.config.yaml` | medium |
| Read `pr.auto_merge` from the working tree (round-1 design) | Simpler, no `git` dependency | **Self-granting:** a PR could add the field to its own diff and merge itself — a security veto in round-1 review; rejected | n/a (never shipped) |
| `AIDAKIT_BYPASS=1` per merge | Already exists | Bypass is a conscious, logged human override, not a declared, recurring policy; using it as a toggle erodes what the bypass means | low |
| Merge via a direct API call to the host, bypassing the hook | Doesn't touch the hook | Hides the exception instead of recording it; adds an HTTP dependency + credential to the engine; tunnels under the guardrail instead of registering it | medium |
| Register as a spec in `docs/specs/` instead of an ADR | n/a | No spec corpus exists in this repo; a decision with rejected alternatives is an ADR by [ADR-003](ADR-003-shared-knowledge-in-docs.md)'s boundary and [ADR-005](ADR-005-command-namespacing.md)'s precedent | low |
