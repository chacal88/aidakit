# ADR-010: The acceptance-leash mirrors the doc-leash — separate agent, weak-bar validator, both flows, max_visits from day one

- **Status:** accepted
- **Date:** 2026-07-24

## Context

The kit has one mechanical leash on the PR gate today: the **doc-leash**. `aidakit:doc-planner` authors a `doc-manifest.json`, `check-doc-manifest.js` verifies each required document exists on disk, and the `check_docs` step of both flows blocks the PR until the list is 100% ([full.yaml:308-316](../../governance/flows/full.yaml), [fast.yaml:193-201](../../governance/flows/fast.yaml)). The leash is deterministic (Node validator, exit 0/1/2) and the enforcement is at the flow, not in the model's prose.

The **acceptance criteria** — the goals `aidakit:brainstorm` extracts in the `full` flow, or the ones authored inline in `proposal.md` for the `fast` flow — carry no such leash. They live as prose in `brainstorm.json` and `proposal.md`; nothing between "the model wrote them" and "the PR opens" checks that each promise was mapped to a real evidence artifact. This is the gap [EPIC-flow-engine-leashes](../roadmap/epics/EPIC-flow-engine-leashes.md) Feature 2 named ("Coleira das metas — `brainstorm` emits `acceptance-manifest.json` (goal → how to verify) and `check-acceptance.js` locks the `pr` step while any criterion has no test/evidence mapped — same treatment as the doc-leash").

The design space had four choices to resolve — each with a wrong answer that would have surfaced during implementation or review. This ADR fixes them together because they interlock (weakening any one of them opens a bypass of the others).

## Decision

**1. A dedicated agent `aidakit:acceptance-planner` authors the manifest — not `aidakit:brainstorm`, not `aidakit:plan`.** The agent is a mirror of [aidakit:doc-planner](../../agents/doc-planner.md) in shape (frontmatter, tools `Read, Glob, Grep, Write`, `model: sonnet`, GOVERNANCE.md §7 anatomy) and in role (author of a manifest that a validator enforces, not the executor of the criteria). Reasoning: `aidakit:brainstorm` is deliberately `Write`-less (isolated context; returns prose only; see [agents/brainstorm.md:4](../../agents/brainstorm.md) — `tools: Read, Glob, Grep, AskUserQuestion`); giving it Write would collapse the two purposes (extract requirements → author artifacts) and force one long-running session to hold both contexts. Overloading `aidakit:plan` has the mirror problem: `plan` authors proposal/design/tasks, and a manifest is a separate artifact whose lifecycle is per-flow-visit (re-authored on every revision), not per-plan. A dedicated agent keeps each role Write-scoped to exactly one deliverable, matches the doc-planner precedent, and keeps `brainstorm`/`plan` contracts stable.

**2. The validator `check-acceptance.js` is weak-bar: it verifies each evidence path resolves on disk with `existsSync + isFile`, and does NOT re-execute tests.** Mirror of [check-doc-manifest.js](../../governance/validators/check-doc-manifest.js) in output contract (`{validator, ok, change_id, level, required, resolved, errors[]}`) and exit semantics (0 pass / 1 incomplete / 2 usage). Reasoning: `hardening` (in `full`, via `aidakit:test`) and `implement`'s `aidakit:test` invoke (in `fast`) already re-run the suite; a leash that re-executes doubles the tail cost for no additional signal. The leash's job is a distinct one — *"the promise was mapped to a real artifact"* — which is a static check, not a runtime check. Keeping the two separate keeps the diagnostics readable: a broken test fails at `hardening`; a lying manifest fails at `check_acceptance`.

**3. The leash gates BOTH `full` and `fast`.** In `full`, the criteria source is `.aidakit/tasks/<change-id>/brainstorm.json` (produced by `aidakit:brainstorm`). In `fast`, there is no brainstorm step; the criteria source is a NEW `## Acceptance criteria` section of `proposal.md` that this decision introduces — distinct from the existing `## Exit criteria` section (which lists validator commands / green-suite gates and stays as-is; see [engine-max-visits/proposal.md](../archive/2026-07-24-engine-max-visits/proposal.md) §Exit criteria for the shape). Observable-effect promises live in `## Acceptance criteria`; validator commands live in `## Exit criteria`; the two do not merge. Existing archived / in-flight proposals are grandfathered (they predate the leash and will never re-enter the flow) — only new changes from this PR onward carry the section. A shared helper `governance/acceptance/parse-criteria.js` normalizes either source into the same `[{ id, criterion, source }]` shape the agent consumes; the helper reads `## Acceptance criteria` (never `## Exit criteria`) when `brainstorm.json` is absent. Reasoning: excluding `fast` would leave the smaller changes without the leash, and small changes are exactly where a promise-to-evidence gap is easiest to miss (fewer artifacts to notice the omission against). **`check-acceptance.js` is the enforcement point for the parser's semantics**: the agent authors the manifest by re-deriving `parse-criteria.js`'s mapping under LLM judgment (it has no `Bash` tool to shell out to the module), so the validator is the sole runtime *consumer* of `parse-criteria.js` — it re-parses the change's live source and confirms every criterion the parser extracts has a corresponding manifest entry (`criterion-orphan` otherwise). This is what makes "single-owner" true in practice rather than by assertion: drift between the agent's re-derivation and the module fails the leash mechanically.

**4. `check_acceptance`'s back-edge to `acceptance` carries `max_visits: 3` + `on_max_visits: acceptance_escalation` from day one, consistent with the just-merged [engine-max-visits](../archive/2026-07-24-engine-max-visits/proposal.md).** Reasoning: the acceptance-manifest is the model's own map of promises to evidence; a broken map that never clears indicates the model cannot reconcile its promises against the plan (either the criteria are wrong or the evidence does not exist). Three rounds is enough — the fourth entry escalates to a `human_gate` (`options: [abort]`) that hands to the human out-of-band, same shape as `specify_escalation`. Shipping without the cap would repeat the exact debit `engine-max-visits` was created to close (an unbounded back-edge with no ceiling); adding the cap in a follow-up would leave a live loop in the tail during the interim.

## Consequences

- **Positive:** the goal-leash mirrors the doc-leash's shape one-for-one — the same three-part pattern (agent → manifest → validator), same output contract, same `n/a`+`condition` waiver semantics; consumers learn once and apply twice. The mechanism the `check_acceptance` cap needs already exists in the engine (no new engine surface). Both flows are covered from day one. Weak-bar keeps the tail cheap (one validator invocation, not a second test run). The dedicated agent keeps `brainstorm` and `plan` contracts stable.
- **Negative:**
  - **The leash adds a new tail step pair** — `document → check_docs → acceptance → check_acceptance → pr` — extending each flow's happy-path length by two steps. **Accepted:** the doc-leash added the same length in its time; each additional gate is the price of the mechanical enforcement.
  - **A change with no acceptance criteria at all** (a pure typo fix, say) still runs `acceptance-planner`, which then must decide either "manifest with `required: []`" (rejected by the validator as `manifest-invalid`) or escalate. **Mitigated:** the agent escalates rather than emits an empty manifest — a change genuinely without criteria is a red flag, not a normal case; the fast flow's `## Acceptance criteria` section being MANDATORY (this decision, point 3) makes the escalation self-detecting.
  - **The manifest is re-authored on every visit** (per [design.md](../archive/2026-07-24-acceptance-leash/design.md) §Re-run semantics), which produces a re-write on the disk for every `critic: revise → specify` cycle. **Accepted:** it's a JSON write over an isolated read of the plan; cost is negligible compared to `aidakit:plan`'s spec re-authoring. Simpler than any "criterion diff" detection primitive.
  - **The weak-bar leaves an intentional residual** — an evidence file that exists but fails at runtime is not caught here. **Mitigated by design:** that failure surfaces at `hardening` (`full`) or `implement`'s `aidakit:test` (`fast`), which are the correct owners of runtime verification. The leash and the test runner do not overlap by construction.
  - **Coupling to `engine-max-visits`** — the leash cannot ship until the `max_visits` mechanism is in `main`. **Satisfied:** the [engine-max-visits](../archive/2026-07-24-engine-max-visits/proposal.md) change landed before this one; the dependency is a fact, not a risk.

### Review trigger

Revisit if the weak-bar starts letting through evidence paths that reviewers repeatedly find to be trivially satisfied (a `file` kind pointing at an empty `.md`, say — which technically resolves but does not observe anything). The correct move would be a stronger `kind`-aware check (per-kind validation rules), not a re-execution — this ADR would gain an amendment naming the new bar. Also revisit if `docs-onboarding.yaml` or a consumer-authored flow adopts the leash and finds the slot ordering (`document → check_docs → acceptance → check_acceptance → pr`) too coarse — the current ordering is justified in [design.md](../archive/2026-07-24-acceptance-leash/design.md) §Slot decision; changing it would be a new decision, not an extension of this one.

## Alternatives considered

| Option | Pros | Cons | Cost to undo |
|---|---|---|---|
| Overload `aidakit:brainstorm` with Write and let it emit the manifest directly | One fewer agent | Collapses `brainstorm`'s isolated-context contract; forces a long-running session to hold both extraction and authoring; contradicts the doc-planner pattern that the kit already applies for the doc-leash | medium |
| Overload `aidakit:plan` with the manifest as a fifth artifact | Symmetry with the four plan artifacts | Wrong lifecycle (plan artifacts are per-change; the manifest is per-visit-to-the-slot); makes `plan` responsible for two failure modes (spec critique via `critic` and evidence mapping via `check_acceptance`), muddying the escalation semantics | medium |
| Strong-bar validator (re-execute the tests each criterion points to) | Catches broken tests earlier | Duplicates `hardening`; doubles tail cost; conflates two distinct failure modes (broken test vs lying manifest) in the same diagnostic; adds framework coupling (the validator would need to know how to run the referenced tests) | medium |
| Gate only `full`, not `fast` | Smaller change surface | Leaves small changes without the leash, which is where evidence-mapping omissions are hardest to notice; splits the kit into two behavior modes for no principled reason | low |
| Ship without `max_visits` on `check_acceptance`, add it in a follow-up | Simpler first cut | Repeats the exact debit `engine-max-visits` was created to close; adds a known-live-loop step to the tail and requires a second PR to close it | low |
| Slot acceptance before `check_docs` (`acceptance → check_acceptance → document → check_docs → pr`) | Fails on manifest problems earlier | An acceptance-manifest failure could mask a doc-manifest failure by pre-empting it; the debugging order becomes "fix docs, then re-run and see if acceptance still fails" — more painful than the reverse | low |
| Parse fast-flow criteria from `tasks.md` (either instead of, or in addition to, `proposal.md`) | The brainstorm assumption 2 named `tasks.md` alongside `proposal.md` as a candidate document | `tasks.md` is scoped to implementation checklist granularity (`- [ ] write test X`), not observable-effect promises; two sources would create ambiguity about which is authoritative when they disagree, and would force the parser + the agent to resolve conflicts across documents. `proposal.md`'s new `## Acceptance criteria` section keeps the source single and unambiguous | low |
| Register the design as a spec in `docs/specs/` instead of an ADR | n/a | No spec corpus exists in this repo; the four decisions have rejected alternatives, which is an ADR by [ADR-003](ADR-003-shared-knowledge-in-docs.md)'s boundary and [ADR-005](ADR-005-command-namespacing.md)'s precedent | low |
