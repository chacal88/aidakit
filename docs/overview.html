Development kit · v0.4 · plugin reference

The aidakit field guide

A Claude Code plugin that carries a full engineering process into any repo: guided architecture design, a spec-driven execution pipeline with human gates, document & execution doctrine enforced by an active hook, an in-repo roadmap, and shared knowledge — no Jira, no Confluence, the truth is always the disk.

29 skills 12 agents 5 validators 4 flows 1 hook 139 tests green

The kit's one idea: a deterministic engine does the enforcing, the AI does the thinking. Anything mechanical — validating docs, blocking dangerous git, deriving status, checking a manifest — runs as zero-dependency Node and cannot be talked out of it. Anything that needs judgment is a skill or an agent. The two halves never blur.

01

The four layers

Everything in the kit belongs to one of four layers. This is the whole product, top to bottom.

Layer 1 · design

Architecture design

/aidakit:design

A sequential 4-phase interview with gates — 1 Business → 2 DDD Modeling → 3 Architecture (decisions become ADRs) → 4 Implementation (hands the baton to the pipeline). One question at a time; each phase yields a document in docs/design/ and only advances on explicit approval.

State lives in docs/design/STATE.md — close the session, resume weeks later.

Layer 2 · pipeline

Execution pipeline

/aidakit:build

Each change runs the canonical cycle from plan to PR (see the strip below). Skills delegate to agents with separated roles — author ≠ reviewer ≠ shipper. The kit stops at the PR URL; the human merges.

Change artifacts live in docs/features/<change-id>/ (or openspec/changes/). One key ties it all: change-id = branch = PR suffix = archive dir.

Layer 3 · doctrine

Document & execution doctrine

/aidakit:docs /aidakit:governance

DOCS.md — the standardized document architecture: canonical docs/ tree, seven inviolable rules (ADR is WORM, every dir has an index, dated archive…), a placement decision tree, WORKING → DURABLE.

GOVERNANCE.md — how agents work: permissive by design with exactly 3 human escalations (merge a PR, supersede an ADR, go out of scope). Enforced by the active pre-bash hook.

Layer 4 · catalog

Catalog & archive

/aidakit:catalog

A grouped, searchable index of everything you have — authored skills, agents, hooks, doctrine, installed official plugins, and a verified community archive loaded on demand. Ask "do I have something for X?" and it points you to the tool.

05

The deterministic engine

Pure Node, zero dependencies. This is the "leash" — mechanical enforcement the model cannot argue with. Every validator follows the same contract: exit 0/1/2, JSON on stdout, a human report on stderr.

pre-bash hook

Runs before every Bash command, blocks what GOVERNANCE §4 forbids (push --force, add -A, reset --hard, gh pr merge…). Fail-open: when in doubt, allow. Bypass via AIDAKIT_BYPASS=1 is logged.

hooks/pre-bash.js

flow engine

A declarative state machine that runs a flow as steps (invoke · runs · human_gate · loop · parallel · terminal). Inversion of control: it pauses and asks the operator to dispatch a skill, then routes on the outcome.

check-doc-manifest

06

Tracking & memory — in the repo

The newest layer: planning and shared knowledge without an external tool. Both live in docs/, versioned and PR-reviewed.

docs/roadmap/

Epic → Feature → Change as markdown. Epics group features; features point to changes by change-id. Status is derived from disk, never a hand-edited field — so it can't drift like a Jira board. ROADMAP.md is generated.

aidakit:roadmap · ADR-002

docs/knowledge/

Durable shared knowledge that is neither a decision nor a how-to: conventions, glossary, gotchas, context. Filled by promotion — learn proposes moving a durable lesson here via PR.

aidakit:learn §7 · ADR-003

.aidakit/memory/

The operational funnel: learnings.md, one line per lesson, read at the start of the next build. Durable entries get promoted up into docs/knowledge/.

07

How to use it

Install once per project, then two starting points: design a new project from zero, or execute the next change on an existing one.

  1. Install in any repo. 
    /plugin marketplace add /Users/kauesantos/Documents/winker/aidakit
/plugin install aidakit@aidakit
  2. New project → design first. Run /aidakit:design and answer the 4-phase interview. It writes docs/design/ + ADRs and, at phase 4, produces the change backlog. judgment
  3. Existing repo → adopt the structure. Run /aidakit:docs (init mode) to deploy the canonical docs/ tree (decisions, guides, knowledge, roadmap…) without steamrolling what's there.
  4. Execute a change. Run /aidakit:build — it picks the next ready change (roadmap gives the order) and drives the cycle: plan → readiness → TDD → review → ship. You approve the gates; the kit stops at the PR URL.
  5. You merge. Merge on the git host. Then aidakit:docs archives the change (it flips to done on the roadmap on its own) and aidakit:learn proposes any DNA or knowledge to promote.
  6. Check status anytime. aidakit:roadmap for Now/Next/Later, /aidakit:catalog to find a tool, /aidakit:governance when a command was blocked and you want to know why.
⚙

Configure per project via aidakit.config.yaml: the content language, the domains.by-path map (which globs belong to which domain, and their strictness order), and the review.matrix (which reviewers each flag summons). Absent → sensible defaults, English.
