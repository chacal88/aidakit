# Coleiras mecânicas do flow engine

Goal: fechar os pontos onde a coleira do flow depende de comportamento do modelo em vez de mecânica verificável — caps, metas, paralelismo e memória de retry passam a ser estruturais no engine/validators, nunca doutrina em prosa.

Origem: análise de gaps sobre `governance/flows/*.yaml` + `governance/engine/` (2026-07-22). Ordem por risco + valor: 1–2 corrigem buracos de coleira ativos; 3–4 são evolução estrutural; 5 é capacidade nova do build (registro diferido) — fora do tema coleira, mas mesma superfície (engine/CLI).

## Features

- **Feature:** Cap mecânico de retries — changes: engine-max-visits
  - Aceite: uma aresta de retorno visitada >N vezes cai em `human_gate` de escalação ("N rounds sem consenso: intervir ou abortar?"), nunca em loop infinito; N configurável por step no YAML. Hoje o "capped rounds" vive só no texto do skill `aidakit:review`.
- **Feature:** Coleira das metas — changes: acceptance-leash
  - Aceite: o brainstorm emite `acceptance-manifest.json` (meta → como verificar) e `check-acceptance.js` trava o step `pr` enquanto houver critério sem teste/evidência mapeada — mesmo tratamento do doc-leash (`check-doc-manifest.js`). **Entregue** — PR #36 (novo agente `aidakit:acceptance-planner`, validador `check-acceptance.js` com cross-validação contra `parseCriteria()`, wiring nos dois flows com `max_visits: 3` no back-edge, ADR-010); dogfooded no próprio PR — o step novo gateou a si mesmo, exit 0.
- **Feature:** Retry com memória — changes: retry-memory
  - Aceite: ao voltar para `implement`, o agente recebe histórico estruturado das tentativas (round, causa da falha em cada uma); os eventos de correção alimentam `aidakit:learn` como matéria-prima de DNA (erro recorrente ≥3x). **Entregue** — `governance/__tests__/retry-memory.test.mjs` 87/87, `engine.test.mjs` 149/149 (ver [evidence.md](../../archive/2026-07-24-retry-memory/evidence.md)); PR de merge para `main` ainda em aberto.
- **Feature:** Fate do `type: parallel` do engine — changes: engine-parallel-fate
  - Contexto (2026-07-24, brainstorm de `flow-parallel-bench` abortado — flow `full-260724-20b372`): `governance/README.md` e `governance/engine/steps/parallel.js` descrevem o `type: parallel` como código morto que roda branches em sequência ("not used by any shipped flow"). O paralelismo real do bench já vive DENTRO do skill e é enforced por `check-bench.js` via `bench.ndjson` (janela de dispatch/retorno). Expressar o bench como `type: parallel` no YAML sem tocar o engine é teatro — dá menos garantia estrutural que hoje, não mais. A entrada anterior ("Bench paralelo estrutural — `flow-parallel-bench`") confundia "o engine tem um `parallel` type" com "o bench melhora".
  - Aceite: decisão do dono registrada em ADR novo — uma das duas trilhas, não ambas:
    - (a) **Deletar**: remover `governance/engine/steps/parallel.js` do parser + validator + tipos; nenhum flow shipado usa; o step type induz erro (a próxima tentativa de "melhorar o bench" cai na mesma armadilha).
    - (b) **Reescrever pra concorrência real**: `Promise.all` sobre branches, política de falha/timeout/ordem, semântica de resume com writes de estado concorrentes, preservação do invariante de overlap; então migrar o bench pra ele. Escopo grande — provavelmente vira EPIC próprio.
- **Feature:** Registro diferido no build (débito) — changes: add-debit
  - Aceite: `/aidakit:flow-fast` ganha um modo registro-apenas — o pedido vira change no roadmap (backlog) + flow pausado estacionado, sem plan/implement; o `resume` retoma para o planejamento sem re-explicar o contexto. Assunção em aberto (brainstorm pulado por delegação do dono): a forma — novo verbo do CLI, flow `register.yaml` ou input do `fast` — é decidida no plan.
- **Feature:** Arquivamento do loop-var-resume (bookkeeping) — changes: archive-loop-var-resume
  - Aceite: `docs/features/loop-var-resume/` movido via `git mv` para `docs/archive/2026-07-22-loop-var-resume/` (data de merge do PR #5, `2026-07-22T19:54:51Z`), `derive-roadmap-status.js --root .` verde (change não declarado no roadmap na época — só sai da área de trabalho, nenhuma linha de status muda; regen do `ROADMAP.md` apenas se a visão derivada mudar), PR `chore(docs): archive loop-var-resume` para main parado na URL — o merge é sempre humano.
- **Feature:** `runs` distingue erro de infraestrutura de veredito negativo — changes: runs-error-routing
  - Aceite: o step `runs` separa "comando/módulo ausente" (erro de infra: surge e interrompe o flow) de "validador julgou NÃO" (exit≠0: roteia normalmente via `on_failure`) — hoje um `Cannot find module` sai como exit≠0 comum e entra em loop de correção via `on_failure` em vez de expor o erro real (achado em `validator-path-resolution`, owner's request §"Observação sobre prioridade").
- **Feature:** Request livre vs change-id nos flows — changes: flow-request-vs-change-id
  - Aceite: `select` reporta o change-id como output estruturado (`resume … success change_id=<id>`, coleira fail-closed no engine) e todo caminho `.aidakit/tasks/…`/`.aidakit/dna/…` dos flows chaveia em `${context.select.change_id}`; valores `${…}` em `command` viajam como dado de ambiente (`$AIDAKIT_VAR_n`, ADR-006) — um request multilinha nunca mais explode um `runs` (exit 127 / "test: too many arguments" da captura `full-260724-ca264a`) nem entra em loop implement↔check; regressão coberta em `engine.test.mjs` §9. **Entregue** — PR #18 (fix + ADR-006), `engine.test.mjs` 127/0; arquivamento do pacote em PR separado (esse mesmo).
- **Feature:** Caminho absoluto do validador nos `runs` steps — changes: validator-path-resolution
  - Aceite: `governance/engine/steps/runs.js` injeta `AIDAKIT_GOVERNANCE` (kit's `governance/` dir via `import.meta.url`) no env de todo child de `runs`, e os 3 flows shipados (`fast.yaml`, `full.yaml`, `docs-onboarding.yaml`) trocam `node governance/validators/…` por `node "$AIDAKIT_GOVERNANCE/validators/…"`; `engine.test.mjs` deixa de fabricar o `governance/` via `symlinkSync` (o teste passava contra realidade falsa) — sem o symlink os casos vão RED contra o código pré-fix e GREEN após. **Entregue** — PR #12/#14. Débito nascido daqui: `agent-validator-paths` (mesma classe de defeito, mas em Bash sessions de agente/skill/command que não passam pelo `runs`).
- **Feature:** Caminho de validador para invocações diretas de agente/skill/command — changes: agent-validator-paths
  - Aceite: as invocações diretas de validador/CLI ensinadas a agentes/skills/commands (`agents/orchestrator.md:50`, `agents/doc-planner.md:155`, `skills/roadmap/SKILL.md:64`, e os mapeamentos de verbo `cli.js` em `commands/flow-fast.md`, `commands/flow-full.md` e `commands/flow-design.md` — escopo ampliado pelo brainstorm, owner-approved) resolvem o caminho do kit independente do cwd — hoje carregavam o mesmo defeito de caminho relativo que `validator-path-resolution` corrigiu nos flows, mas por um vetor que o `AIDAKIT_GOVERNANCE` injetado pelo `runs.js` não alcança (essas sessões Bash não passam pelo `runs` step). Mecanismo: hook `SessionStart` (`hooks/session-start.js`) exporta `AIDAKIT_GOVERNANCE` para a sessão inteira; guard fail-closed (`: "${AIDAKIT_GOVERNANCE?...}"`) em cada um dos 18 pontos de chamada; registrado em `ADR-012` (amenda `ADR-004`).
- **Feature:** Status derivado do git compartilhado (single-valued entre worktrees) — changes: roadmap-status-from-shared-git
  - Aceite: `derive-roadmap-status.js` deriva `in-progress`/`done` do estado git COMPARTILHADO (dir committado em qualquer branch via `git ls-tree` por ref, O(branches), sem varrer worktree) unido à working-tree local; a resposta é a mesma de qualquer worktree/clone; sem git, degrada pra disk-only idêntico ao anterior. Registrado em `ADR-007` (amenda `ADR-002`). **Entregue** — PR #21, `roadmap.test.mjs` 28/28.
- **Feature:** Commit precoce do plano no `full` flow (fecha a janela do ADR-007) — changes: flow-commit-plan-early
  - Aceite: passo `commit_plan` (tipo `runs`) entre `specify` e `critic` em `governance/flows/full.yaml` — assim que o plano é autorado, `docs/features/${context.select.change_id}/` é stageado e commitado, e o deriver enxerga `in-progress` a partir de qualquer worktree/clone; best-effort e fail-safe (guard `test -n` para id vazio/não resolvido; `on_success` e `on_failure` vão ambos pra `critic`; `git diff --cached --quiet` evita commits vazios em plano revisado); registrado em `ADR-009` (completa `ADR-007`). **Entregue** — commit `38a83ac` via PR #24, `engine.test` 127/127.
- **Feature:** `classify` declares structured `domain` output instead of leaking `outcome` — changes: flow-request-classify-domain-contract
  - Acceptance: `governance/flows/full.yaml`'s `classify` step declares `outputs: { success: [domain] }` (mirroring `select`'s `change_id` output) and `brainstorm`'s `domain: "${context.classify.outcome}"` interpolation (currently `full.yaml:61`) reads the declared `domain` value instead of the control-flow `outcome` string; fail-closed resume semantics when `--domain` is absent, mirroring the `flow-request-vs-change-id` precedent above. Requires a dedicated ADR extending [ADR-006](../../decisions/ADR-006-flow-values-as-data.md) §Decision-2 to `classify` before the flow YAML changes (`flow-shape-change-gets-adr`). Identified as finding F1 in `docs/features/workflow-script-optimization/inventory.md` §4.
- **Feature:** Split `hardening`'s mechanical suite-run from its anti-hardcode judgment — changes: hardening-anti-hardcode-split
  - Acceptance: `governance/flows/full.yaml`'s `hardening` step (`invoke_target: aidakit:test`) splits into a `runs` step (repo test command + coverage-threshold check, both already mechanical predicates) followed by a narrower `invoke` step scoped only to anti-hardcode/hard-DoD judgment; mirrors the acceptance-leash shape ([ADR-010](../../decisions/ADR-010-acceptance-leash.md) — dedicated judgment agent as writer, deterministic script as validator) as a new instance, not a fourth leash pattern. Requires a dedicated ADR defining the split (routing, and whether the judgment step still gates on a mechanical suite failure) before the flow YAML changes. Identified as candidate C2 in `docs/features/workflow-script-optimization/inventory.md` §5.
- **Feature:** Cheap nit-revision path on capped invoke steps — changes: flow-nit-revision-path
  - Acceptance: when a critic/bench round returns ONLY mechanical nits (a bounded, purely textual fix — e.g. a one-word count correction), the flow offers a path where the runner applies the fix inline and the SAME reviewer confirms on the live tree, without consuming one of the step's capped `max_visits` dispatches; precedent: `workflow-script-optimization` commit `fa580e5` ("Three"→"Four" in `design.md` §6, applied by the runner instead of burning the 3rd and last `specify` dispatch, critic re-verified before resume). Requires a dedicated ADR defining what qualifies as a "nit" mechanically (size/scope bound) and how the confirmation is ledgered, so the path can't become a cap bypass. Registered 2026-07-29 from the `learn` step of `workflow-script-optimization` (learning L4, proposal PU-3).
